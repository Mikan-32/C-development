# AI-2 データ品質の判定

- 状態：提案
- 使う人：`analysis/`（判定）、`ui/`（理由の表示）
- PRD：4.1「取得状況の表示」、4.2「分析できない場合は理由を表示」、7 章
- 画面との照合：UX-7（`docs/ux/UX-7_states.md` と、PR #65 の改訂版）と照らし合わせた（2026-11-24）。Q01〜Q11 の文言は一致。出す順番と次の行動の出し方を 3 章に書き足した

## 1. 夜ごとの判定

用語：`D` = 計測した時間（終了 − 開始）、`V` = 有効なエポック（`acc_cov` ≥ 0.8）の合計時間。

| 判定 | 条件（上から順に調べる） | 画面での扱い |
|---|---|---|
| **取得失敗** `FAILED` | 加速度を開始できなかった、または `V` < 30 分、または分析処理がエラーで終わった | スコア・段階は出さない。理由と次の行動を出す |
| **不足** `INSUFFICIENT` | `V` < 3 時間、または `V / D` < 0.7、または `NK_EPF_OFFBED` のエポックが有効なエポックの 30% 超 | スコアは「参考値」付き。傾向の計算には使わない |
| **分析可能** `OK` | 上のどれにも当てはまらない | すべて表示 |

実機では、加速度を開始できないときはセッションを保存しない（AI-1 の 2 章）。そのため Q02 は夜の結果には残らず、計測を始めようとした画面で出す。参照実装（`tests/eval/nk_ref.py`）の `acc_start_failed` は、この場合を試すための入力。

## 2. 項目ごとに「出せるか」

夜が `OK` でも、項目ごとに条件を満たさなければ表示しない（AI-6）。

| 項目 | 出す条件 |
|---|---|
| 睡眠時間・寝つき・中途覚醒・効率 | 夜が `OK` か `INSUFFICIENT` |
| 深い・浅い | 夜が `OK` |
| いびき | マイクを使い、`mic_cov` ≥ 0.8 のエポックが 70% 以上 |
| 呼吸数 | 睡眠中のエポックの 50% 以上で `breath_q` ≥ 0.6 |
| 規則性（スコアの項目） | 直近 7 日に `OK` の夜が 3 夜以上 |
| 週の傾向・比較のフィードバック | 期間内に `OK` の夜が 3 夜以上（比べる場合は、比べる 2 つの群がそれぞれ 2 夜以上） |

## 3. 理由コード

画面の文言は UX-7 と共通。文言は「何が起きたか」と「次にどうするか」を必ず含め、ユーザーを責めない。

| コード | 名前 | 判定への影響 | 画面の文言（案） | 次の行動 |
|---|---|---|---|---|
| Q01 | マイクの許可なし | いびき・呼吸音なし | マイクを使わずに計測しました。いびきは記録していません | 設定でマイクを許可する |
| Q02 | 加速度センサーを使えない | 取得失敗 | この端末では体の動きを計測できませんでした | 端末を再起動して、もう一度試す |
| Q03 | 計測が短い | 取得失敗 | 計測が 30 分より短かったため、分析していません | 次の夜も計測する |
| Q04 | 計測が途中で止まった | 欠損 | 3:10〜4:40 は計測できていません（アプリが停止しました） | 電池の最適化の設定を見直す |
| Q05 | 取れた割合が少ない | 不足 | 計測できた時間が全体の 7 割に届きませんでした | 充電しながら計測する |
| Q06 | 有効な計測が短い | 不足 | 計測できた時間が 3 時間に届かなかったため、参考値です | — |
| Q07 | ベッドの上にない疑い | 不足 | スマホがベッドの上にないようでした | 枕元のマットレスの上に置く。「置き方を確かめる」で試し計測（4 章）へ |
| Q08 | マイクを使えなかった時間 | いびきの一部なし | 通話などでマイクが使えない時間がありました | — |
| Q09 | 電池が少なく停止 | 欠損 | 電池が残り 5% になったため、計測を止めました | 充電しながら計測する |
| Q10 | 夜の数が足りない | 傾向なし | 傾向は 3 夜分の記録がそろうと表示されます | 続けて計測する |
| Q11 | 分析のエラー | 取得失敗 | 分析を完了できませんでした。データは保存されています | 「もう一度分析する」 |

Q04 は、加速度の欠損すべてに付く（CS-2 の実装）。文の「（アプリが停止しました）」は、`end_reason` が `SERVICE_KILLED` の夜の最後の区間にだけ付け、ほかの区間は「3:10〜4:40 は計測できていません」だけにする。

### 3.1 理由の決め方と保存のしかた

| コード | 決め方 |
|---|---|
| Q01 | `session.mic_used` = 0 |
| Q02 | 加速度を開始できなかった（1 章の下の注のとおり、夜の結果には残らない） |
| Q03 | `V` < 30 分 |
| Q04 | `acc_cov` < 0.8 が 2 エポック以上続いた区間がある。区間は `reason` = `Q04` の `GAP_START`／`GAP_END`（AI-1 の 5 章） |
| Q05 | `V / D` < 0.7 |
| Q06 | `V` < 3 時間 |
| Q07 | `NK_EPF_OFFBED` のエポックが、有効なエポックの 30% 超 |
| Q08 | `NK_EPF_MIC_BUSY` のエポックがある。区間は `reason` = `Q08` のイベント（CS-2 の実装は、マイクの欠損 `NK_EPF_GAP_MIC` の区間も Q08 にしている） |
| Q09 | `session.end_reason` = `BATTERY_LOW` |
| Q10 | 期間内の `OK` の夜が 3 夜未満。夜ごとには保存せず、傾向を出す画面で決める |
| Q11 | 分析処理がエラーで終わった |

`night_result.reasons`（AI-1 の 7 章）は、ビット n を Qn に使う（ビット 0 は使わない）。参照実装の `Q` と同じ。例：Q04 と Q07 の夜は `(1 << 4) | (1 << 7)` = 144。

### 3.2 理由が複数あるとき

UX-7 の帯は画面に 1 つだけなので、帯には次の順で最初の 1 つの文を出す。直し方がはっきりしているものを先にする。ほかの理由は、日別の詳細（LG-02）の取得状況にすべて並べる。

| 状態（UX-7） | 順番 |
|---|---|
| 取得失敗 `ST-FAILED` | Q03 だけ（Q11 は `ST-ANALYSIS-FAILED` として出す） |
| 不足 `ST-INSUFFICIENT` | Q07 → Q05 → Q06 |
| 一部が取れていない `ST-PARTIAL-GAP` | 帯ではなく 1 行。区間ごとに、時刻の順に並べる（Q04・Q08）。Q09 は最後に出す |

### 3.3 次の行動の出し方

UX-7 の未決（次の行動がボタンにならない場合）への AI 側の案。

| 出し方 | コード |
|---|---|
| ボタン（押す先がある） | Q01（マイクの許可）、Q04（電池の最適化の設定）、Q07（置き方を確かめる）、Q11（もう一度分析する） |
| 文だけ（押す先がない） | Q02、Q03、Q05、Q09、Q10 |
| 出さない | Q06、Q08 |

UX-7 の `ST-INSUFFICIENT` の次の行動「置き方を確かめる」は、Q07 のときのボタン。Q05・Q06 のときは上の表のとおりに切り替える。

## 4. 試し計測（置き方の確認）

初回設定と、計測開始の前（任意）に 10 秒間計測する。

| 結果 | 条件 | 文言 |
|---|---|---|
| `OK` | `acc_cov` ≥ 0.9 かつ `micro_mg` ≥ 0.5 | 置き方は大丈夫です |
| `WARN` | `micro_mg` < 0.5（揺れがほとんどない＝机の上などの疑い） | 体の近く、マットレスの上に置いてください（このまま始めることもできます） |

## 5. テスト観点（AI-7 で確認する）

- 欠損を入れた合成データで、判定と理由コードが表のとおりになること
- 境界値（`V` = 29 分 59 秒／30 分、`V / D` = 0.69／0.70）で判定が切り替わること
- `FAILED` の夜にスコアと段階が出力されないこと
- 理由が複数ある夜で、帯に出す文が 3.2 の順番になること
